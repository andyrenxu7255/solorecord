# Synology SSO + ASR Architecture

This document records the recommended integration design for SoloRecord when it
is distributed as an APK that must sign in through Synology SSO before use.

## Executive decision

Do not put Bailian/DashScope API keys, local ASR service secrets, LLM keys,
Synology client secrets, or Hermes workspace tokens in the APK.

Use a small server-side gateway. The APK should only contain:

- Gateway base URL
- Public app identifier
- Non-secret feature flags

The gateway should hold:

- Synology SSO/OIDC client secret, if required
- ASR credentials, whether local/private or Bailian/DashScope
- ASR model selection
- LLM API key and meeting-minutes prompt
- Object storage credentials or STS role
- Hermes/sales-workspace forwarding credentials
- Retry queue state

This is needed for security and for operational stability. The phone should
focus on reliable recording, login, playback, and sync. The gateway/local ASR
service should handle audio preprocessing, ASR, meeting-minutes generation, and
forwarding.

See `docs/local-asr-pipeline.md` for the preferred local ASR audio-processing
pipeline.

## ASR deployment choice

Preferred target architecture:

- APK records and uploads rolling audio segments.
- Gateway validates Synology login and owns all processing jobs.
- Local/private ASR service performs VAD, format normalization, optional
  denoise/dereverb, optional speaker diarization, and transcription.
- LLM service generates meeting notes and person-specific action items.
- Gateway forwards the structured payload to Hermes/sales workspace.

Bailian/DashScope can remain a vendor adapter, but it should not be the only
architecture path. If Bailian Qwen3-ASR-Flash-Filetrans is used, the model does
not accept a private phone-local file directly. It expects a publicly reachable
audio URL, then returns a task id, and the caller polls until the task completes.

## What "offline transcription" means here

For Bailian/Qwen ASR, "offline" means non-real-time cloud file transcription. It
does not mean fully on-device speech recognition without network.

Recommended ASR model:

- Long recordings: `qwen3-asr-flash-filetrans`
- Short recordings only: `qwen3-asr-flash`

Important behavior:

- `qwen3-asr-flash-filetrans` is asynchronous only.
- It supports long files, but the audio must be provided through a publicly
  accessible URL.
- The caller submits a task, receives `task_id`, polls the task endpoint, then
  downloads the result JSON from the returned `transcription_url`.
- The returned result URL is temporary, so the gateway must download and persist
  the transcript promptly.
- Qwen-ASR currently does not provide speaker diarization. If "specific person"
  action items are required, owner assignment should be generated by the LLM
  from transcript context, participant names, or a later manual correction UI.
  If true speaker separation is mandatory, evaluate Fun-ASR/Paraformer where
  supported.

## Is URL + key + model id enough?

For a quick prototype with short audio, endpoint + API key + model id can call
`qwen3-asr-flash`.

For the target production APK, it is not enough:

- APK secrets can be extracted.
- Long-file transcription needs audio hosting, task submission, polling, result
  download, retry handling, and transcript normalization.
- Synology login for a native app is cleaner and safer when a gateway handles
  the confidential side of the OAuth/OIDC exchange.
- Hermes forwarding should be server-side so sales workspace credentials never
  ship to phones.

## Recommended runtime flow

1. User opens APK.
2. App checks local login session.
3. If not logged in, App opens Synology SSO login through the gateway/OIDC flow.
4. Gateway validates Synology identity and returns an app session token.
5. User taps Start Recording.
6. App creates one meeting session id and starts a foreground recording service.
7. Service writes rolling audio segments locally, for example:
   `files/audio/{meetingId}/part_0001.m4a`.
8. User taps End Recording, or app close triggers service shutdown.
9. App finalizes the current segment atomically and marks the meeting as
   `recorded`.
10. When network is stable, WorkManager uploads missing segments to the gateway.
11. Gateway stores audio and starts the audio-processing pipeline: normalize,
    VAD, optional denoise/dereverb, optional diarization, ASR, and transcript
    merge.
12. If a cloud file-transcription adapter is selected, the gateway additionally
    handles audio hosting, task submission, polling, and result download.
13. Gateway calls the configured LLM to generate meeting notes, summary, and
    person-specific action items.
14. Gateway forwards the structured meeting payload to Hermes/sales workspace.
15. App syncs status and displays transcript/summary/action items in Records.

## App tabs

### Recording

- The tab is disabled until the user is logged in.
- One tap starts recording.
- A second tap stops recording.
- Closing the app should stop recording through lifecycle handling, but recording
  should run in a foreground service while the app is backgrounded.
- Rolling segment duration should be short enough to minimize loss on crash. A
  practical default is 3 to 5 minutes per segment.
- Keep every segment until upload and server acknowledgement complete.

### Records

- One user start/end cycle is one record, even if the audio has many segments.
- The record stores segment paths, upload status, transcription status, summary
  status, and forwarding status.
- Playback should play the segment list in order.
- Transcript timestamps should be merged with per-segment offsets.
- "整理会议" should enqueue processing if network is unavailable.

### Login Status

- Shows current Synology user and token expiry.
- Provides Login and Logout.
- Logout removes the local app session and stops access to recording/records
  until login succeeds again.

## Gateway API sketch

The mobile app can stay simple if the gateway exposes stable business endpoints:

```text
GET  /mobile/config
POST /mobile/auth/start
POST /mobile/auth/exchange
POST /mobile/meetings
POST /mobile/meetings/{meetingId}/segments/{segmentNo}
POST /mobile/meetings/{meetingId}/finish
POST /mobile/meetings/{meetingId}/process
GET  /mobile/meetings
GET  /mobile/meetings/{meetingId}
POST /mobile/meetings/{meetingId}/forward
```

The app authenticates these calls with the gateway-issued session token, not the
Bailian key.

## Synology SSO setup inputs

Prepare these for implementation:

- Public HTTPS domain for Synology SSO Server
- SSO Server well-known URL or OAuth/OIDC endpoints. Current server config
  supports explicit authorize/token/userinfo/JWKS URLs and can also infer the
  older Synology-style `/webman/sso/SSOOauth.cgi` and
  `/webman/sso/SSOAccessToken.cgi` endpoints from `SOLO_SSO_ISSUER`.
- OIDC application id/client id
- Redirect URI registered in Synology
- Client secret, stored only on gateway if the chosen flow requires it
- Test user account and required group/role rules

Synology's server URL must be a valid HTTPS domain, not an IP address or
QuickConnect URL. Plan DNS and TLS before APK testing.

## Bailian setup inputs

Prepare these for the gateway:

- Region/scope: Chinese mainland Beijing or International Singapore
- DashScope/Bailian API key for that region
- ASR model: `qwen3-asr-flash-filetrans`
- Submit endpoint:
  - Beijing: `https://dashscope.aliyuncs.com/api/v1/services/audio/asr/transcription`
  - Singapore: `https://dashscope-intl.aliyuncs.com/api/v1/services/audio/asr/transcription`
- Task polling base:
  - Beijing: `https://dashscope.aliyuncs.com/api/v1/tasks/`
  - Singapore: `https://dashscope-intl.aliyuncs.com/api/v1/tasks/`
- Optional parameters: language hint, `enable_itn`, `enable_words`, channel id
- Object storage bucket or a gateway-hosted signed audio URL mechanism

## Implementation notes for the current Android project

Current code now includes:

- Android three-tab UI: Recording, Records, Login Status.
- Foreground recording notification plus rolling local audio segments.
- `MeetingRecord` with grouped `AudioSegment` records.
- Local playback for recorded segments.
- Server-backed sync, transcript, summary, action items, exports, APK release
  upload/download, and model/provider admin page.
- Speaker rename by stable speaker id, updating every matching transcript row.
- Server-side Synology SSO redirect/callback skeleton plus demo login fallback.

Before wider rollout:

- Replace Android Base64 segment upload with multipart or resumable upload for
  very long meetings.
- Move Android session token storage to EncryptedSharedPreferences/Keystore.
- Connect the final Synology endpoints from the deployed SSO Server.
